## SPRINT 1 — Sequential Dissipative Reservoir Core + Runtime Gate  (~3–4 days) **[HIGHEST RISK]**

**Objective:** Implement the v5 paradigm shift: a genuinely recurrent, dissipative quantum
reservoir (Hou et al. 2026 style), replacing the windowed quantum-kernel design. Establish
whether 12-qubit density-matrix simulation is computationally feasible; make the go/no-go call.

**Scientific spec:**
- State update per hourly step k:  `ρ_k = D_{γ1,γ2} ∘ e^{−iHτ} ∘ U(s_k) [ρ_{k−1}]`
  where:
  - `U(s_k)`: input injection of the 13-feature vector s_k, scaled to [−π, π]. Baseline scheme:
    per-qubit RY(a·x_j) with input-scaling hyperparameter `a` (memory–nonlinearity knob), features
    mapped to qubits round-robin (13 features → 12 qubits: feature 13 folds onto qubit 1 as RZ).
    Keep the ZZFeatureMap available as an alternative injection (`injection="zz"`), default `"ry"`.
  - `e^{−iHτ}`: existing TFIM, J=1.0, g=1.0, first-order Trotter M=10, τ=1.0 (reuse the verified
    CX–RZ–CX / RX decomposition).
  - `D_{γ1,γ2}`: per-qubit amplitude damping (rate γ1) + dephasing (rate γ2) Kraus channels applied
    once per step. **This is the fading-memory mechanism** (Hou: T1 relaxation is pivotal;
    non-unital noise is the resource — this replaces v4's depolarizing-on-angles idea).
- **Washout / rewinding protocol** (Hou): for each labeled sample at time t, rewind and re-drive
  the reservoir from t − n_wo with n_wo = 24 (one day) so the state is initial-condition-free.
  Implement a `washout` parameter; verify ESP by showing trace distance between two random initial
  states after n_wo steps < 1e−2 (reuse the existing ESP machinery, adapted to sequential mode).
- Readout per step (base, pre-multiplexing): the existing 36 single-body + 198 two-body Pauli
  expectations = 234 features from the post-step ρ_t.
- Prediction target: residual architecture unchanged — `ŷ_{t+h} = persistence + f(features_t)`.

**Implementation tasks:**
1. New module `QRCx/reservoir/sequential.py`: class `SequentialDissipativeQRC(BaseReservoir)`
   with `drive(sequence) -> feature matrix`, parameters
   `(n_qubits=12, tau=1.0, trotter_steps=10, gamma1, gamma2, input_scaling, washout=24,
   injection="ry", backend="auto")`.
2. Backend strategy, in order of preference — benchmark all three on a 200-step drive:
   a. Qiskit Aer `density_matrix` with Kraus channels (already a dependency for noise studies);
   b. PennyLane `default.mixed`;
   c. Custom NumPy/CuPy Kraus propagation (234 observables via precomputed Pauli matrices —
      12-qubit ρ is 4096×4096 complex128 ≈ 268 MB; one step = a handful of 4096² matmuls, viable).
   Record steps/second for each; pick the fastest as `backend="auto"`.
3. **Runtime gate (go/no-go):** project the cost of the Sprint 4 pilot
   (4,350 samples × washout 24 ≈ 105k reservoir steps). GO if projected pilot ≤ 12 h wall-clock on
   available hardware. If NO-GO at 12 qubits: (i) drop to 10 qubits, (ii) reduce washout to 12 with
   an ESP check, (iii) cache the driven trajectory so overlapping windows share computation
   (rewinding overlap → compute the full 4,350+24-step trajectory ONCE per hyperparameter setting,
   not per sample — implement this optimization by default; it collapses cost to ~4.4k steps).
   NOTE: trajectory caching is only valid because inputs are identical across samples — document
   the equivalence to the rewinding protocol in the docstring.
4. Unit tests: trace(ρ)=1 preserved each step; ESP convergence under γ1>0; feature matrix shape
   (T, 234); determinism under fixed seed; γ1=γ2=0 + injection="zz" limit reproduces v4-equivalent
   unitary behavior on a toy sequence.
5. Micro-validation on NARMA10 (synthetic, fast): sequential reservoir must beat a linear AR
   readout baseline. This is the standard sanity benchmark (Hou, Fujii-Nakajima). Target
   NMSE < 0.4 in FAST_MODE at 12q; record the number for the paper.

**Definition of Done:** runtime gate decision recorded in sprint log with steps/sec numbers per
backend; NARMA10 sanity pass; ESP verified in sequential mode; tests green.

## SPRINT 2 — Time-Multiplexed Readout + Dissipation Sweep  (~2–3 days)

**Objective:** Multiply readout capacity without adding qubits (Hou's second innovation;
Fujii & Nakajima 2017), and locate the useful dissipation regime.

**Tasks:**
1. Time multiplexing: within each step's τ evolution, measure the observable set at V intermediate
   points t_i = i·τ/V, i=1..V (i.e. after every M/V Trotter sub-blocks). Feature count = V × 234.
   Parameter `multiplexing=V`, default V=4 (936 features), configurable 1..M.
   Implementation detail: with the cached-trajectory approach this costs V observable evaluations
   per step, not V re-simulations.
2. Dissipation sweep (this replaces and corrects the v4 depolarizing study):
   grid γ1 ∈ {0, 0.01, 0.03, 0.1, 0.3}, γ2 ∈ {0, 0.03, 0.1}, input_scaling a ∈ {0.3, 1.0, 3.0},
   V ∈ {1, 2, 4}. Evaluate on (i) NARMA10 NMSE and (ii) MC + IPC decomposition (linear vs
   nonlinear capacity, Čindrak framework). FAST_MODE grid first; refine around the optimum.
3. Produce the paper's key characterization figure: total IPC and its linear/nonlinear split vs γ1,
   for a ∈ {0.3, 1.0, 3.0} — the memory–nonlinearity trade-off surface. Expected qualitative
   result: an interior optimum in γ1 (moderate dissipation beats both unitary and over-damped),
   mirroring Čindrak's reset-length peak. If the optimum is at γ1=0, report it honestly and
   investigate input scaling before concluding.
4. Academic figure style: matplotlib, serif fonts, no titles-in-figure, labeled panels (a)/(b),
   300 dpi, colorblind-safe palette; create `QRCx/experiment/figstyle.py` and use everywhere.

**Definition of Done:** best (γ1, γ2, a, V) configuration frozen in `configs/v5_reference.yaml`
with MC in 5–10 and IPC recorded; trade-off figure saved; tests green.

## SPRINT 5 — IPC-Matched Reservoir Tuning (Novel Contribution)  (~3 days)

**Objective:** The paper's flag. Task-adapted tuning: measure the *demand profile* of the weather
residual target, then tune the reservoir so its IPC supply matches it. No published work does this
for operational weather data.

**Tasks:**
1. Demand profile: on the training split, regress the residual target on delayed inputs and
   low-order Legendre polynomial products thereof (degrees 1–3, delays 0–24) — i.e. estimate which
   (delay, degree) cells carry predictable signal for h=1 and h=6. Output: a demand heatmap
   D(delay, degree). Module `QRCx/metrics/task_demand.py`.
2. Supply profile: the reservoir's IPC decomposition C(delay, degree) as a function of
   (γ1, a, τ) — reuse Sprint 2 machinery.
3. Matching objective: maximize Σ min(C, D) (captured useful capacity) over a coarse (γ1, a, τ)
   grid; compare the matched configuration against the Sprint 2 reference on pilot forecast
   metrics. Hypothesis to test: matched config improves 6h skill; report even if it doesn't
   (rubric rewards honest limitation analysis).
4. Figure: side-by-side demand vs supply heatmaps + captured-capacity bar per configuration.
5. Write the method up in `docs/ipc_matching.md` as a draft paper subsection (with the Čindrak,
   Dambre 2012 'Information processing capacity of dynamical systems', and Jaeger citations).

**Definition of Done:** demand/supply/matching implemented and tested; comparison numbers in
`results/ipc_matching.json`; draft subsection written.

## SPRINT 7 — Dirac-3 Hybrid Stage  (~3 days; start after organizer reply, latest after Sprint 4)

**Objective:** Satisfy the hard requirement "working implementations run on QCi's Dirac-3 via
qBraid" with a scientifically legitimate stage: best-subset readout feature selection as
polynomial optimization.

**Formulation:**
- Binary selection z ∈ {0,1}^F over the V×234 features, cardinality budget K via Dirac-3's native
  sum constraint. Objective: minimize the ridge-validation-error surrogate
  E(z) = −2 Σ_i c_i z_i + Σ_ij Q_ij z_i z_j  (c = feature–target covariances, Q = feature Gram
  matrix on train, both computed on standardized features) — a quadratic polynomial, well inside
  Dirac-3's fifth-order capability; qudit continuous relaxation acceptable with rounding + local
  repair.
- Pipeline framing for the write-up: Stage 1 quantum reservoir (simulator / gate QPU) →
  Stage 2 readout sparsification on **Dirac-3** → Stage 3 classical ridge on selected features.
- Baseline comparison: Lasso path and greedy forward selection at the same K (Dirac-3 must be
  compared, not just used); report validation RMSE vs K curves for all three.

**Tasks:**
1. `QRCx/readout/dirac3_selector.py` using `qci-client` (job build, submit, poll, decode,
   sum-constraint handling, retries, result caching to `results/dirac3/`).
2. Local simulated-annealing stand-in behind the same interface (`solver="sa"`), so development
   never blocks on device allocation, and CI never needs credentials.
3. Runs at K ∈ {32, 64, 128} on the frozen full-benchmark features; final model option
   `readout="ridge+dirac3"` evaluated on the test set once.
4. Document device parameters actually used (num_samples, relaxation schedule, allocation seconds)
   — judges require concrete numbers.
5. Adapt to whatever the organizer clarification said; if they meant something different by
   "three stages," record the delta and adjust framing, not the science.

**Definition of Done:** at least one successful Dirac-3 job with decoded solution committed to
results; RMSE-vs-K comparison figure (Dirac-3 vs Lasso vs greedy); write-up subsection drafted.
