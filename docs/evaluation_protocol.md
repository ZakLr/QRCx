# Evaluation Protocol — Sprint 3

Defines the fairness protocol every baseline (and the QRC) is held to, and
documents the diagnosis of the pre-Sprint-3 broken ESN/ARIMA baselines.
Every number cited here is traceable to a `results/*.json` file
(generated by `scripts/generate_baselines.py` / `scripts/esn_diagnosis.py`)
or to a run recorded in this document with its exact command, per project
policy.

## 0. Split ledger (Sprint 3 closeout addendum)

**Canonical split**: train 2019-2022 / val 2023 / test 2024
(`QRCx/data/splits.py::temporal_split`). **All development decisions —
hyperparameter tuning, model selection, DoD/gate checks — are made on val
only.** Test-2024 is reserved for a one-time final confirmatory report,
not for iterative sprint-by-sprint development.

Enforcement: `QRCx/data/split_guard.py::assert_test_unlocked()` raises
`TestSplitLockedError` unless called with `unlocked_by=UNLOCK_TOKEN`
(reserved for the Sprint 6 confirmatory runner) or
`QRCX_UNLOCK_TEST_SPLIT=1` is set. `scripts/generate_baselines.py` and
`scripts/esn_diagnosis.py` both take `--split {val,test}` (default
`val`) and call the guard before any `--split test` run.

**Every number in this document, by split:**

| Result | Split | File |
|---|---|---|
| ESN diagnosis (broken/fast/full-grid stages, DoD check) | **val** | `results/esn_diagnosis_val.json` |
| Full baseline table (persistence/ARIMA x2/ESN x N/null control/residual/GBM ceiling probe) | **val** | `results/baselines_val.json` |

**Test-set touch ledger** (historical — computed before this addendum,
before the val/test discipline above was made explicit; kept for

above as the project's reference numbers going forward):

| Result | Split | File | Status |
|---|---|---|---|

| First full baseline table run | test | `results/baselines_test_HISTORICAL.json` | Superseded by val run (§5) |

The DoD's headline number (tuned ESN skill at 1h) was re-verified on val
and is *stronger* there than on test (+12.9% vs. +6.2% at h=1 — see §2),
so this was not a case of a test-set-flattered number quietly failing
re-verification; it is logged and re-run per policy regardless.

## 1. Data and features (single source of truth)

- Real NOAA ISD-Lite hourly data, station KORD (USAF 725300, WBAN 94846),
  2019-01-01 through 2024-12-31, loaded via the frozen
  `QRCx/data/loader.py` (never modified — wrapped only).
- **13 engineered features** (`QRCx/data/preprocessor.py::build_features`,
  ported from `pipeline_demo.py::engineer_features`, replacing the
  previous 10-feature set — see README "Known limitations", now closed):
  `T_db, T_dew, RH, WS, SLP, WD, Wx, Wy, T_dep, hour_sin, hour_cos,
  doy_sin, doy_cos`.
- **Residual/target definition (frozen, single source of truth)**:
  climatological anomaly `ε_t = (y_t − μ_climo(month,day,hour)) / σ_climo`,
  with `μ_climo`/`σ_climo` computed on the **train split only**
  (`compute_climatological_normals` + `StandardScaler.fit` on train,
  `.transform` on val/test). The first-difference definition is
  deprecated and not used anywhere in this pipeline.
- **Strict temporal split**, no shuffling: train 2019-2022, val 2023, test
  2024 (`QRCx/data/splits.py::temporal_split`). `TimeSeriesSplit` is used
  for every in-split cross-validation (Ridge/KRR readouts).
- 24-hour input window (`W=24`); ~1-1.4% missing readings (SLP, WD) mean
  roughly a third of 24h windows are dropped for containing at least one
  NaN (`sliding_windows`'s `valid` mask) — real, not a bug, and every
  baseline is scored on the identical retained window set (see §3).

## 2. Diagnosis: the pre-Sprint-3 ESN failure

**Symptom**: ESN-500 skill of roughly -400% to -1400% vs. persistence at
1h on real KORD data (reproduced: -705.9% at h=1, -53.5% at h=6 with a
frozen replica of the pre-Sprint-3 `baselines/esn.py`, see the table
below).

**Root cause — wrong target/input alignment, not a hyperparameter
problem**: the previous implementation flattened each QRC-style 24x13
window into a single ~312-dim vector and fed reservoirpy one such vector
per training sample, relying on reservoirpy's own sequential-input
convention (each row = one timestep). Consecutive samples share 23/24
hours of overlap, so the "sequence" reservoirpy actually processed was a
highly redundant, discontinuous re-encoding of the true hourly series —
not a signal an ESN's recurrent memory can exploit for short-lag
prediction. A secondary contributing bug: `reservoirpy.nodes.Reservoir`'s
leak rate (`lr`) was never set, silently defaulting to 1.0 (no leaky
integration) — poorly suited to a task dominated by strong 1h-lag
autocorrelation (persistence is a very strong baseline at h=1: RMSE
0.197 vs. std 1.41).

**Fix** (`QRCx/baselines/esn.py`):
1. Feed reservoirpy the **genuine raw hourly sequence**
   (`preprocess()`'s new `train_seq`/`val_seq`/`test_seq` outputs — the
   scaled anomaly series before windowing), with `prepare_sequential_targets`
   aligning input row `i` to target `seq[i+h, target_col_idx]` — reservoirpy's
   native, correct convention.
2. Grid-search `spectral_radius ∈ {0.7,0.9,0.99,1.1}`,
   `leak_rate ∈ {0.1,0.3,0.6,1.0}`, `input_scaling ∈ {0.1,0.5,1.0}`,
   `ridge α ∈ logspace(-8,-1,8)` (384 combinations), `washout=100`,
   **selected on the validation split only** (`tune_esn`).
3. Predictions are aligned back to the windowed pipeline's exact
   NaN-filtered sample set via `test_valid_idx` (see §3) for a fair,
   identical-target comparison against every other baseline.

**Result** (real KORD data, ESN-200, `scripts/esn_diagnosis.py --split val`
-> `results/esn_diagnosis_val.json`, the authoritative, val-scored,
DoD-verifying run — see §0):

| Stage | h=1 skill | h=6 skill |
|---|---|---|
| Pre-Sprint-3 (broken, frozen replica) | -533.9% | -14.4% |
| Fixed alignment, fast grid (4 combos) | -29.7% | +15.6% |
| Fixed alignment, full grid (384 combos) | **+12.9%** | **+24.6%** |

Statistical significance vs. persistence (full-grid stage, DM test HAC-
corrected `maxlags=h-1`, 2000-replicate moving-block bootstrap 95% CI on
the skill difference — both from `results/esn_diagnosis_val.json`):

| h | DM stat | DM p-value | Skill-diff 95% CI |
|---|---|---|---|
| 1 | -11.01 | ~0 | [+10.5%, +15.4%] |
| 6 | -9.50 | ~0 | [+20.1%, +28.9%] |

Both CIs exclude 0 and the DM p-values are ~0 — the ESN's improvement
over persistence is not noise at either horizon.

(A test-2024-scored run of the same three stages,
`results/esn_diagnosis_test_HISTORICAL.json`, gave -705.9%/-53.5% (broken),
-58.8%/+8.0% (fast grid), +6.2%/+14.6% (full grid) — same qualitative
story, val-2023 happens to be an easier period for this model. Superseded
by the val run per §0; kept for the ledger, not deleted. An even earlier
ad hoc run of the broken-window-flattening logic against a slightly
different split ordering measured -401.9%/-28.5% at h=1/h=6 — same
failure mode, run-to-run variance from the untuned, effectively-random
reservoir seed choice at the time.)

**DoD check**: tuned ESN achieves skill ≥ -5% vs. persistence at 1h on
val-2023 — **met** (+12.9%, full grid, statistically significant). No
amount of hyperparameter tuning fixed the pre-Sprint-3 version because
the bug was in what sequence was fed to the reservoir, not which
hyperparameters it used — confirmed by the fast-grid result already
crossing from catastrophic (-533.9%) to competitive (-29.7%) purely from
the alignment fix, before any tuning improvement was applied.

## 3. Target alignment for non-windowed baselines

`sliding_windows()` now also returns `valid_idx` per split
(`train_valid_idx`/`val_valid_idx`/`test_valid_idx`): the window-start
positions retained after dropping NaN-containing windows. Any baseline
that consumes the raw (non-windowed) sequence directly — ESN, ARIMA — must
align its per-position predictions via `pred[valid_idx + W - 1]` to
reproduce exactly that split's `data["y_<split>"]` sample set. Verified:
`len(pred[valid_idx + W - 1]) == len(y_<split>)` for every split, by
construction (see `baselines/esn.py::forecast` docstring for the
derivation).

## 4. Diagnosis: the ARIMA "same forecast for every horizon" bug

**Symptom**: the previous `baselines/arima.py::forecast()` fit one ARIMA
model, called `.forecast(steps=len(y_test))` once, and returned the
*identical* array for every requested horizon — h=1 and h=6 predictions
were bitwise identical, silently wrong for any h > 1.

**Fix**: fit once on the raw chronological train sequence, forecast a
trajectory of length `len(test_seq) + max(horizons) - 1`, and slice
`fc[h-1 : h-1+n_test]` per horizon (the standard multi-step-ahead ARIMA
convention, matching `pipeline_demo.py`'s reference FSDH-curve code) —
aligned via §3 like ESN.

**Separate, honestly-reported finding (not fixed — order is spec-fixed at
(2,1,2))**: ARIMA(2,1,2) on real KORD data performs very poorly (skill
around -5000% at h=1). Diagnosis: `d=1` differences an already-stationary
climatological-anomaly series (order fixed by the Sprint 3 spec, not
retuned here) — a classic over-differencing misconfiguration. Reported
as-is per project policy (`docs/sprint_log/SPRINT_2_5_REPORT.md`'s
convention of reporting negative results honestly rather than hiding
them); not a target-alignment bug, and the spec fixes the order.

### 4b. Auto-selected ARIMA(p,0,q) — a second, non-strawman line

Per the Sprint 3 closeout addendum: "we fixed the strawman-ESN problem;
let's not leave a strawman-ARIMA in its place." `baselines/arima.py`
adds a second table entry, `arima_auto`
(`select_order_by_aic` + `auto_order_forecast`): AIC-selected `(p, 0, q)`
order (`p, q ∈ {0..3}`, `d=0` fixed — avoiding the over-differencing
issue by construction, not by retuning the spec-fixed model) fit on
train only, forecast on val.

**A second, deeper bug found while building this**: `forecast()`'s
single `len(eval_seq) + max(horizons) - 1`-step trajectory, generated
once from the end of train and sliced per horizon, is not just
over-differenced — it never incorporates the real val data as it
becomes available. Any stationary ARMA process's h-step forecast decays
toward its unconditional mean as h grows, so evaluating deep into that
one trajectory (thousands of steps from train's end) is close to a
constant-value forecast almost regardless of order. Confirmed
empirically: even the AIC-selected `(3, 0, 2)` order — `d=0`, no
over-differencing — scored **-4857%/-350%** skill at h=1/h=6 through the
single-trajectory path, nearly as bad as the spec-fixed `(2,1,2)`'s
failure, despite fixing the `d=1` issue. `pipeline_demo.py`'s reference
implementation uses the identical single-trajectory convention, so this
was inherited, not introduced by the Sprint 3 ESN-alignment fix.

**Fix for the `arima_auto` line specifically**:
`rolling_origin_forecast` re-anchors to real observed history every
`stride` steps (default `max(horizons)`) via `ARIMAResults.apply(...,
refit=False)` — a cheap Kalman-filter state update reusing the already-
fitted parameters, no re-optimization. Each block of `stride` positions
shares one h-step-ahead forecast anchored at the block's start; a
documented, tractable compromise (not a fresh forecast at literally every
position), but drastically more local than one trajectory for the whole
eval period. Result: **-650%/-50%** skill at h=1/h=6 (val-2023,
`results/baselines_val.json`) — a large improvement over both the
spec-fixed line and the single-trajectory auto-order attempt, but still
honestly worse than persistence and ESN at these short horizons. Reported
as a genuine, fair result — not forced to look better than it is; ARIMA
is simply not competitive with persistence/ESN on this short-horizon,
strongly-autocorrelated task, even given a fair chance.

The spec-fixed ARIMA(2,1,2) line (`arima`) is kept exactly as specified
— single-trajectory, `d=1` — as the literal spec baseline; `arima_auto`
is the fair-chance line. Both appear in `results/baselines_val.json`'s
`metrics`.

## 5. Fairness protocol

Every baseline below uses the identical 13 features, identical strict
temporal split, and identical `StandardScaler` fit on train only.

| Baseline | Module | Notes |
|---|---|---|
| Persistence | `baselines/persistence.py` | Floor. |
| ARIMA(2,1,2) (`arima`) | `baselines/arima.py::forecast` | Spec-fixed order, single trajectory; §4. |
| ARIMA(p,0,q) auto (`arima_auto`) | `baselines/arima.py::auto_order_forecast` | AIC-selected order, rolling-origin local forecast; §4b. |
| ESN (dimension-matched) | `baselines/esn.py` | nodes = QRC `n_features` (234 at 12 qubits; `baselines/fairness.py::dimension_matched_esn_size`; ESN-936 example in the spec = 234 x V=4 multiplexing). |
| ESN-500 / ESN-5000 | `baselines/esn.py` | Scaling story. |
| Residual-ESN | `baselines/esn.py` (`residual=True`) | Predicts `seq[t+h]-seq[t]`, the same anomaly-residual target `architecture/residual.py::ResidualQRC` predicts; persistence added back at predict time. |
| Null control: Ridge / KRR | `baselines/fairness.py::null_control_forecast` | Fit directly on the **flattened raw 24x13 window** — no reservoir. If this matches QRC skill, the reservoir buys nothing. |
| Residual-Ridge | `baselines/fairness.py::residual_ridge_forecast` | Same residual target as Residual-ESN/ResidualQRC, flattened-window features. |

All ESN variants are tuned via `tune_esn` (§2), selected on the
validation split only, never test.

### 5b. GBM predictability-ceiling probe (not an RC-comparison baseline)

`baselines/fairness.py::gbm_ceiling_probe_forecast`:
`HistGradientBoostingRegressor` on the flattened raw 24x13 window,
briefly tuned on val (3x3 grid over `max_iter`/`max_depth`), scored on
val at `h ∈ {1, 3, 6, 12}`. Reported under `results/baselines_val.json`'s
top-level `ceiling_probes` key, **not** merged into `metrics` — it
answers a different question than the fairness table ("does the
reservoir help against classical models"): how much headroom exists in
these 13 features above what ESN/Ridge/KRR extract, given a model class
that can freely fit nonlinear interactions. Doubly interesting now that
the ESN clears its own DoD bar (+12.9%/+24.6%): the GBM ceiling tells us
whether there's room left above that for a future architecture change,
not whether the reservoir "worked."

## 6. Metric harness

`QRCx/metrics/forecast.py`: RMSE, MAE, NRMSE, skill, VPT.
`QRCx/metrics/fsdh.py`: FSDH, `compute_fsdh_curve` (h=1..48 in
`scripts/generate_baselines.py`).
`QRCx/metrics/significance.py` (new, Sprint 3):
- `diebold_mariano`: squared-error-loss DM test with Bartlett/Newey-West
  HAC variance correction, `maxlags = h - 1` (standard h-step-ahead
  convention). Unit-tested to match `statsmodels.OLS(..., cov_type="HAC")`
  exactly (`tests/test_significance.py`) at h=1 and h=6.
- `moving_block_bootstrap` / `skill_difference_ci`: block bootstrap
  (Kunsch 1989, block length `n**(1/3)`) 95% CI for skill(model) -
  skill(baseline), recomputing the ratio-based skill statistic on each
  resample rather than assuming a Gaussian/linear statistic.

`scripts/generate_baselines.py` runs a DM test and a skill-difference
bootstrap CI vs. persistence for every RC-comparison baseline (not the
GBM ceiling probe — §5b) at every eval horizon and writes them into
`results/baselines_<split>.json`. `scripts/esn_diagnosis.py` additionally
runs both for its full-grid ESN stage specifically (§2).

## 7. Known scope cuts (reported honestly, not hidden)

- **ESN-5000 at the full 384-point grid** was not run this session:
  `results/esn_diagnosis_val.json` measured a single full-grid ESN-200
  fit+tune; `results/baselines_val.json` (FAST_MODE, 4-point grid, full
  real dataset) measured the reduced grid for dim-matched(234)/ESN-500
  (see that file's `wall_clock_s`). Extrapolating (384/4 = 96x the grid,
  plus 5000/200 = 25x the units) puts a full-grid ESN-5000 run at many
  hours — out of this session's time budget. `--no-fast-mode` on
  `generate_baselines.py` runs it; left for a follow-up sprint rather
  than blocking Sprint 3 on it.
- **Null-control KRR training set capped at 3000 samples**
  (`generate_baselines.py`'s `KRR_MAX_TRAIN`): `KernelRidge` is O(n^2) in
  training samples (dense kernel matrix, refit per grid point per CV
  fold); at the full ~22-35k training windows this is intractable. This
  is a pre-existing limitation of `KRRReadout` used pipeline-wide
  (e.g. `readout="krr"` on `DirectQRC`/`ResidualQRC`), not new to
  Sprint 3 and not fixed here (out of scope) — only capped for this
  specific null-control baseline so the script completes. The eval set is
  never subsampled, only the KRR fit's training tail.
- **`arima_auto`'s rolling-origin forecast re-anchors every `stride`
  steps, not every single position** (§4b): a documented tractable
  compromise (`ARIMAResults.apply(refit=False)` per anchor is cheap but
  not free; per-position refiltering over ~8-35k eval hours was judged
  not worth the wall-clock for a baseline that's already honestly
  non-competitive at these horizons).
- **Circular quantity `WD`** (wind direction, degrees) is kept as a raw
  anomaly-differenced feature, matching `pipeline_demo.py`'s established
  convention — not addressed here (pre-existing, inherited unchanged).

## 8. Reproducing the results

```
python scripts/generate_baselines.py --fast-mode --split val      # ~15-20 min, dev/CI (ARIMA auto-order AIC search dominates)

python scripts/esn_diagnosis.py --split val                       # DoD-verifying ESN-only run, ~10 min

# test-2024 is locked (see §0); requires an explicit unlock, logged as a
# new ledger entry, not a routine dev command:
QRCX_UNLOCK_TEST_SPLIT=1 python scripts/generate_baselines.py --split test
```
