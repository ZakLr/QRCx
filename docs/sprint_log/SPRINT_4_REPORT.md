# Sprint 4 (REVISED) — Pilot Evaluation: Paradigm Go/No-Go

**Bottom line**: real, complete pilot evaluation on real KORD weather data
(train 2019-2021, eval 2022), both architectures (v4 windowed statevector
QRC, v5 sequential dissipative density-matrix QRC), against a full
classical fairness protocol. **V1 (paradigm validation): PASS.** The
dissipative mechanism produces a real, statistically significant forecast
skill improvement over persistence (v5 residual, h=12: +14.4%, Diebold-
Mariano p≈0) that a same-architecture ablation confirms depends
specifically on dissipation (vanishes to ~0% when gamma1=0). **V2
(competitive verdict): FAIL.** The best QRC result still loses to
dimension-matched ESN at 3 of 4 horizons, and loses to a plain linear
Ridge control (no reservoir at all) at every horizon. **Branch: B** —
paradigm validated, not yet practically competitive. Four real bugs were
found and fixed along the way (not hidden), documented below with the
exact numbers each one changed.

## 0. Data and protocol

Pilot split (nested inside the canonical locked train block, never
touching val=2023/test=2024): train 2019-2021 (26,304 hourly steps),
eval 2022 (8,760 hourly steps). 13 engineered features, climatological-
anomaly residual target, `StandardScaler` fit on train only — same single
source of truth (`QRCx.data.preprocessor.preprocess()`) as every other
sprint. Horizons {1, 3, 6, 12}h per the Sprint 4 spec (not the canonical
[1,6]) — required re-running the export step after an early run silently
used the wrong default and produced two mislabeled result rows (caught
before it went further; see Bug 3 below is unrelated but this alignment
bug was the very first thing caught and fixed, in `scripts/
sprint4_export_pilot_seq.py`).

Two GPU architectures evaluated, both on an on-demand qBraid H200
instance (real, confirmed: `HAS_CUPY: True`, `nvidia-smi` showed 100%
utilization and tens of GB in use during real runs):

- **v4** (`scripts/sprint4_v4_gpu_handoff.py`): windowed statevector
  simulation (ZZFeatureMap encode + TFIM Trotter evolution), batched
  across all windows simultaneously (no per-sample recurrence — the
  windowed architecture re-encodes fresh per sample). Run at both 16 and
  20 qubits (see Bug 2).
- **v5** (`scripts/sprint4_v5_gpu_handoff.py`): sequential dissipative
  density-matrix reservoir, 12-qubit reference config, driven
  continuously over the real hourly sequence (genuine recurrence).

Classical fairness protocol (`scripts/sprint4_pilot_baselines.py`,
generated by a background CPU run): persistence, ARIMA(2,1,2),
ESN-dimension-matched (234 units, matching the 12-qubit QRC feature
count), ESN-500, Residual-ESN, null-control Ridge/KRR (no reservoir,
flattened raw window), Residual-Ridge. Every non-persistence model
scored with Diebold-Mariano test + moving-block bootstrap CI vs.
persistence, at every horizon.

## 1. Real bugs found and fixed

### Bug 1 — `ZZFeatureMap` double-applying every gate (production code, real, significant)

`QRCx/QRCx/encoding/zz_feature_map.py::circuit()` called `qml.apply(op)`
on operators that PennyLane had **already auto-queued** at construction
time (since `encode()` builds them inside the active QNode's recording
context). Confirmed with a minimal repro: constructing `qml.Hadamard(wires=0)`
then `qml.apply()`-ing it inside an active qnode produces `|0⟩`, not `|+⟩`
— every gate was applied twice. For Hadamards (H·H = I, nothing
intervening) this **completely cancelled them out** — the encoder never
actually created superposition from `|0...0⟩` — and every RZ/IsingZZ
angle was silently doubled. Found while cross-validating a from-scratch
GPU reimplementation of this exact circuit (`sprint4_v4_gpu_handoff.py`)
against the real PennyLane output and finding they disagreed by O(1).

**Fixed**: `encode()` now builds ops inside
`qml.QueuingManager.stop_recording()` so `circuit()`'s explicit
`qml.apply(op)` is the only queuing event. Verified the fixed circuit
matches the from-scratch reimplementation to ~1e-8 at multiple
n_qubits/n_layers/trotter_steps combinations. Full test suite (33/33)
still green after the fix — no regressions.

### Bug 2 — v5's per-step CPU↔GPU roundtrip (found via real observed throughput, fixed twice)

`extract_correlators_dm` (correlator readout) and part of `_inject` (the
13th-feature-onto-qubit-0 phase, which fires every step for our real
13-feature/12-qubit data) both forced a full 12-qubit density-matrix
GPU→CPU→GPU roundtrip **every single step**. Real-world consequence: v5
could not complete even 500 steps within the qBraid instance's observed
~45-minute forced-stop interval (see Bug 4). Fixed by rewriting both to
stay entirely on the GPU array module until the very end (a small
feature vector, not the full density matrix, is what actually needs to
leave the GPU) — **0.36 s/step measured**, verified numerically identical
to the old implementation (max diff ~3.5e-9) before deploying.

Still too slow for the full ablation's time budget, so profiled further:
the correlator extraction was doing ~700+ individual small GPU calls per
step (a transpose+trace per qubit and per qubit-pair), and per-call
dispatch overhead — not raw FLOPs — was the real bottleneck. Rewrote it
again as a handful of large vectorized gather operations (same math,
expressed as diagonal sums and off-diagonal element sums instead of
partial traces via reshape+transpose). Verified exact match (rel err
~1e-16) against the already-validated reference. Real result: **0.36 s/step
→ 0.072 s/step**, another ~5x. Combined: **~75x total speedup** from
where this started.

### Bug 3 — NaN in the continuous sequence (real, found live on the GPU)

`train_seq`/`val_seq` (the raw continuous per-hour sequence v5 drives)
still contain NaN at real KORD ISD's missing SLP/WD readings (613/26,304
train rows, 219/8,760 val rows — real numbers). v4's windowed
`X_train`/`X_val` are already NaN-free (the windowing pipeline drops any
window containing one), but v5 drives the raw sequence continuously with
no windowing, so a single NaN timestep corrupts the recurrent density
matrix for every step after it — silently, until it finally surfaced as
`sklearn.Ridge: Input X contains NaN` 44 minutes into a real drive.

**Fixed** in `scripts/sprint4_export_pilot_seq.py`: forward-fill (per
column, per split, never leaking across the train/val boundary or using
future values) with a backward-fill fallback for NaN in a split's very
first rows. Standard, defensible handling for continuous state-space
methods fed real sensor data.

### Bug 4 — qBraid infrastructure instability (external, not our code, real cost)

The on-demand H200 instance auto-stopped repeatedly (~26-68 minutes into
each session, cause not confirmed from the CLI's available diagnostics)
regardless of active GPU load. Added resumable checkpointing to both GPU
scripts (v4: per-batch feature array + progress index; v5: full density
matrix + step index + features-so-far every 500 steps — this one needed
its own bug fix, an off-by-one that would have double-applied one step's
injection/evolution/dissipation onto an already-updated ρ, caught via a
byte-for-byte uninterrupted-vs-simulated-crash-resume test before
deploying). Separately, one specific instance got permanently stuck in a
"Resume failed, try again" loop across 6 consecutive attempts — abandoned
it and provisioned a fresh instance rather than continuing to retry a
broken one. Also caught and reversed a near-miss: `qbraid compute up
<profile>` was tried as a workaround and provisions a **new** instance
rather than resuming the stopped one — caught within seconds and
terminated the accidental duplicate before it ran up double billing.

makes this architecture carry any predictive signal at all on this task.

### Classical fairness baselines (`results/sprint4_pilot_baselines.json`, real KORD data, same split)

Skill vs. persistence:

| model | h=1 | h=3 | h=6 | h=12 |
|---|---|---|---|---|
| ARIMA(2,1,2) | -5598.5% | -1097.9% | -353.7% | -108.3% |
| ESN dim-matched (234) | -90.8% | +2.06% | +17.9% | +27.5% |
| ESN-500 | -46.0% | +10.2% | +21.6% | +28.4% |
| Residual-ESN | +12.4% | +19.1% | +24.2% | +28.4% |
| null-control Ridge (no reservoir) | +17.0% | +24.2% | +27.3% | +31.6% |
| null-control KRR | -590.7% | -160.7% | -56.3% | -10.0% |
| Residual-Ridge (no reservoir) | +17.1% | +24.3% | +27.3% | +31.6% |

**Honest, load-bearing finding**: a plain linear Ridge regression on the
flattened raw window — no reservoir, quantum or classical — beats every
other model at every horizon, including both ESN variants. This is
exactly the fairness protocol's purpose: it reveals that on this
particular pilot task, the predictive signal is almost entirely linear
and doesn't require any nonlinear reservoir (quantum or classical) to
extract. Neither v4 nor v5 beats this null control at any horizon.

## 3. V1/V2 verdict (`scripts/sprint4_verdict.py`)

- **V1 (paradigm validation): PASS.** At least one QRC cell beats
  persistence by a DM-significant margin (p<0.05) — v5 residual h=12,
  +14.4%, p≈0 — and the ablation confirms this specifically depends on
  dissipation.
- **V2 (competitive verdict): FAIL.** Criterion: best QRC (architecture,
  source) pairing beats dimension-matched ESN's point-estimate skill at a
  *majority* of horizons. Real result: 1/4 (only h=1, where ESN happens
  to be uniquely bad at -90.8%). ESN wins at h=3, 6, 12. (An earlier,
  narrower version of this criterion checked h=1 only and passed almost
  automatically for exactly that reason — caught and fixed before
  trusting it; see `scripts/sprint4_verdict.py`'s inline history.)
- **Branch: B** — paradigm validated, not yet practically competitive.
  Reported as such, not spun as a win.

## 4. Scope deviations (logged, not silent)

- v5's ablation reduced from the original 12 drives (2 gamma1 × 2 V ×
  3 seeds) to 2 (2 gamma1 × 1 V=1 × 1 seed), after an explicit
  conversation with the user about real time constraints. This drops the
  multiplexed-readout (V=4) ablation cell and the seed-stability check.
  Full 3-year training data was still used in both drives that did run.
- v4 was run at 16 and 20 qubits (exceeding the reference 12-qubit
  config) as an exploratory extension, once real measured throughput
  showed this was cheap (~2 min and ~46 min respectively) — flagged as
  out-of-spec relative to the "12 reference / 10 fallback" invariant, not
  silently substituted for the reference config. Both qubit counts show
  the same qualitative result.
- An earlier v4 CPU-only attempt (before the GPU handoff scripts existed)
  used n_qubits=8 (also out of spec) and a subsampled window count due to
  CPU infeasibility at the true reference config (57.5 s/sample measured)
  — that result (`results/sprint4_pilot_v4.json`) is superseded by the
  GPU runs above and kept only for the historical record.
